# Notionデータベース設計

Notionが営業データの正本(SSoT)である。本書は**9つのNotionデータベース**の構成を定義する。

改訂履歴: 2026-08-05 設計レビュー反映(次回アクションDB追加、external_id、長文のページ本文化、契約書URL/ファイル分割、semantic_key、標準ビュー、プロパティID方式)。

## 0. 前提

- Notion APIバージョン: **`2026-03-11`**(最新版)。データベース=コンテナ、データソース=テーブル。各DBは単一データソースで運用し、アプリは**データソースID**を環境変数で参照する。`@notionhq/client` は本バージョン対応リリース以上を使用する。
- ページの削除・ゴミ箱状態の判定は **`in_trash`** フィールドを使用する(`archived` は使用しない)。
- 9つのDBは初期セットアップスクリプト(`scripts/setup-notion.ts`、Phase 1で作成)がAPIで作成し、データソースID・プロパティIDを出力・保存する。親ページ(例: 「営業管理システム」ページ)を手動で用意し、インテグレーションを接続しておく。
- プロパティ名は日本語で統一する(Notion閲覧者にとっての可読性を優先)。ただしアプリの変換層は**プロパティ名ではなくプロパティIDで参照**する(§11)。
- 選択肢系はNotionの `select` / `multi_select` を使わず、**営業マスタDBへのリレーション**にする。理由: 安定ID・表示順・色・有効フラグ・種別・semantic_keyを管理画面から制御でき、ハードコード禁止要件を満たすため。

### 全DB共通プロパティ

| プロパティ | 型 | 備考 |
|---|---|---|
| external_id | rich_text | **アプリが発行するUUID。全ページ必須。** 作成の冪等化・クラッシュ復旧の照合キー([sync-design.md §1](./sync-design.md))。データソースクエリの `rich_text equals` フィルタで検索できる。Notion側で編集しないこと |

### 一括登録の設計

- 複数顧客への一括登録では、**顧客ごとに独立した履歴ページを作成**し、全ページに同一の `batch_id` を付与する(1レコード共有の禁止要件)。各行のexternal_idは `batch_id + 顧客ページID` から決定的に生成し、再実行時の二重作成を防ぐ。

### 既存の「次回アクション」項目との役割整理(重複した正本を作らない)

| 場所 | 役割 |
|---|---|
| **次回アクションDB** | **正本。** 作成・完了・期限変更はすべてここで行う |
| 顧客DB・案件DBの「次回アクション」「次回予定日」 | **導出キャッシュ**(Notion閲覧用)。未完了(semantic_key=open)のうち期限が最短のアクションからアプリが自動反映。手編集は整合性確認で再計算値に戻し警告を記録 |
| 対応履歴DBの「次回アクション(入力記録)」「次回予定日(入力記録)」 | 履歴登録時の入力スナップショット(監査・文脈用)。編集してもアクションDBには影響しない |

- 対応履歴の登録フォームで次回アクションを入力すると、アプリが次回アクションDBに正本レコードを作成し、履歴側には入力記録を残す。
- アクションの完了・取消は次回アクションDBの状態変更で行い、顧客・案件のキャッシュを再計算する([sync-design.md §7](./sync-design.md#7-派生データの再計算dependency_reindex))。

## 8. 営業マスタ DB(単一DB+種別方式)

### 方式と管理範囲の明確化

- **管理者が管理画面から自由に追加・編集・並び替え・無効化できるのは、システムが対応済みのマスタ種別「内」の選択肢**である(例: タグを増やす、営業ステータスの名称・順序を変える)。
- **新しいマスタ種別そのもの**(例: 「顧客ランク」という新しい選択項目)の追加は、参照プロパティ・画面・インデックス列が必要になるため、汎用カスタム項目エンジンを実装しない限り**コード・スキーマ対応が必要**。管理画面には出さず、開発タスクとして扱う。

### プロパティ

| プロパティ | 型 | 備考 |
|---|---|---|
| 名称 | title | |
| マスタ種別 | select | 事業区分 / タグ / 営業ステータス / 案件ステージ / 案件ステータス / 対応履歴分類 / 集客ルート / 優先度 / 契約区分 / 取引区分 / 支払状況 / 契約状態 / クレーム重要度 / クレーム対応状況 / 担当者区分 / アクション状態 |
| **semantic_key** | rich_text | **状態系マスタ用・Phase 1から導入。** 表示名に依存せずコードが状態を一意判定するためのキー(例: `won` / `lost` / `active` / `completed` / `open` / `done` / `cancelled`)。**同一種別内で一意**(設定されている行のみ)。状態遷移・受注集計・アクション未完了判定などに使用 |
| **semantic_tags** | rich_text(カンマ区切り) | **分類系マスタ用。** 複数項目が同じ意味を共有できるタグ集合。例: 訪問=`meeting,visit`、オンライン商談=`meeting,online`。一意性なし。商談件数の判定は「`meeting` を含むか」で行う。Supabaseキャッシュでは `text[]` に展開 |
| 表示順 | number | |
| 色 | select | Notion標準色名 |
| 有効 | checkbox | OFFで新規選択不可(既存参照は維持) |
| 適用事業区分 | relation → 営業マスタ(自己参照・複数可) | 空=全事業区分で利用可 |
| 備考 | rich_text | |

### semantic_key / semantic_tags の使い分け

| 用途 | 使用する列 | 一意性 | 例 |
|---|---|---|---|
| 状態系(1項目=1つの意味状態) | semantic_key | 種別内で一意 | 案件ステータス: 受注=`won`。契約状態: 有効=`active` |
| 分類系(複数項目が意味を共有し得る) | semantic_tags | 一意性なし(共有可) | 対応履歴分類: 訪問=`meeting,visit`、オンライン商談=`meeting,online` |

- 状態系マスタにsemantic_tagsは使わない。分類系マスタにsemantic_keyは使わない(両方設定された場合は同期時に警告)。

### 初期データ

- 営業ステータス(semantic_key): 未接触 / 接触予定 / 接触中 / 担当者接続 / アポイント獲得 / 商談中(`negotiating`)/ 提案・見積 / 検討中 / 受注(`won`)/ 導入・実施中 / 継続フォロー / 保留 / 失注(`lost`)
- 集客ルート: 紹介 / セミナー / 広告 / Web問い合わせ / 展示会 / アウトバウンド / 既存顧客 / パートナー / 自治体・団体経由 / その他
- 事業区分: 介護福祉(インソール) / AIセミナー
- 優先度: 高 / 中 / 低
- 対応履歴分類(semantic_tags): 電話(`call`)/ メール(`email`)/ 訪問(`meeting,visit`)/ オンライン商談(`meeting,online`)/ 資料送付(`document`)/ 見積発行(`quote`)/ DM(`dm`)/ その他
- 案件ステージ(semantic_key): 初回接触 / ヒアリング / 提案 / 見積提示 / クロージング / 受注(`won`)/ 失注(`lost`)
- 案件ステータス(semantic_key): 進行中(`active`)/ 受注(`won`)/ 失注(`lost`)/ 保留(`on_hold`)/ 完了(`completed`)
- 取引区分: 購入 / 受注 / 発注
- 支払状況(semantic_key): 未請求(`unbilled`)/ 請求済(`billed`)/ 入金済(`paid`)/ 滞留(`overdue`)
- 契約状態(semantic_key): 有効(`active`)/ 満了(`expired`)/ 解約(`cancelled`)/ 取消(`void`)
- クレーム重要度: 高 / 中 / 低
- クレーム対応状況(semantic_key): 未対応(`open`)/ 対応中(`in_progress`)/ 完了(`done`)
- 担当者区分: 決裁者 / 担当者 / 窓口
- アクション状態(semantic_key): 未完了(`open`)/ 完了(`done`)/ 取消(`cancelled`)

**コードはこれらの値をロジックにハードコードせず、semantic_key / semantic_tags(masters_cache経由)で判定する。商談件数の集計は対応履歴分類のsemantic_tagsに `meeting` を含むかで判定する。**

## 9. 派生項目の再計算ルール(手作業で不整合にしない)

以下の顧客・案件プロパティは**アプリが自動計算する導出値**であり、利用者が手作業で更新しない。Notion側で手編集された場合は整合性確認・dependency_reindexで再計算値に上書きし、警告を `sync_errors` に記録する。

| 導出項目 | 計算元 | 再計算トリガー |
|---|---|---|
| 顧客.最新対応内容 / 最終対応日 | 対応履歴のうち対応日時が最新のもの(要約・対応日時) | 対応履歴の作成・編集・削除検知 |
| 顧客.次回アクション / 次回予定日 | 次回アクションDBの未完了(open)のうち期限最短のもの | アクションの作成・状態変更・期限変更 |
| 案件.次回アクション / 次回予定日 | 同上(案件に紐づくもの) | 同上 |
| 顧客.見込み金額 | **確定: 導出値。** 案件ステータスのsemantic_keyが `active` または `on_hold` の案件の見込み金額合計 | 案件の作成・金額変更・ステータス変更 |

- 確度を乗じた**加重見込み金額**は初期版では持たず、将来のダッシュボード集計項目(フェーズ2以降)として扱う。

## 10. 長文の扱い(ページ本文ブロック)

対応履歴の本文、クレームの内容・原因・対応内容・再発防止策などの長文は、DBプロパティ(rich_textは2,000字制限があり編集性も低い)ではなく**Notionページ本文ブロック**に保存する。

- DBプロパティには**一覧用の要約のみ**(対応履歴「要約」、クレーム「概要」)を置く。要約はアプリが本文の先頭から自動生成(初期版: 先頭200字)し、手動上書きも可能。
- クレームのページ本文は見出しブロック(「内容」「原因」「対応内容」「再発防止策」)で構造化し、アプリの変換層が見出し単位で読み書きする。
- **本文の更新方法(安全な追加優先方式)**: 「既存ブロックを先に削除してから追加」する方式は、削除後のクラッシュで旧本文が消失するため**採用しない**。以下の順序で行う。
  1. 新しい管理セクション(新ブロック群)を追加する
  2. 読み取りで新ブロックの反映を検証する
  3. 新block_id群を `write_operations.recovery_payload` に記録する
  4. 旧管理セクション(旧ブロック群)を削除する
  状態遷移とクラッシュ復旧手順は [sync-design.md §1](./sync-design.md#ページ本文更新の状態遷移と復旧) に定義する。どの時点でクラッシュしても旧本文は消失せず、重複(新旧併存)は復旧処理で解消できる。
- **本文の監査**: 監査ログには本文全文を保存しない。変更前後の**本文ハッシュ(SHA-256)と要約、文字数**を記録し、「本文が変更された」事実と概要を追跡可能にする(全文が必要な場合はNotionのページ履歴を参照する運用)。
- **本文の更新競合**: プロパティと同様にページの `last_edited_time` で楽観ロックする。編集開始時に取得した値と保存時の値が異なる場合は保存を中止し、再読込を促す。ブロック取得はページネーション(100ブロック/回)に対応する。

## 11. プロパティID方式とスキーマ変更検知

### プロパティID参照

Notionのプロパティ名変更で連携が破損することを防ぐため、変換層は**プロパティIDで参照**する。

- `setup-notion.ts` がDB作成後に各データソースのスキーマを取得し、`{ データソースID, プロパティ名 → プロパティID, 型 }` のスナップショットを生成する。
- スナップショットは `config/notion-schema.generated.json`(リポジトリ管理・レビュー可能)として保存し、あわせてSupabase `system_settings` にも格納する(実行環境が参照する正)。
- 変換層(`lib/notion/converters/`)はスナップショット経由でプロパティIDを解決し、プロパティ名のリテラルをコードに散在させない。

### スキーマ変更検知

- Webhookの `data_source.schema_updated` 受信時、および日次整合性確認時に、現在のスキーマとスナップショットを照合する。
- 不一致(プロパティの削除・型変更・必須プロパティの欠落。名前変更はID参照のため警告のみ)を検知したら `sync_errors`(stage=`schema_mismatch`)へ記録し、**管理画面「同期状況」に管理者向け警告を表示**する。該当データソースの書込は安全のため一時停止できる。

### リレーションの件数制限(25件超)への対応

ページ取得APIのレスポンスでは、リレーション等の複数値プロパティは**先頭25件までしか含まれない**(`has_more` が付く)。変換層は以下を必ず実装する。

- `has_more: true` の場合、「ページプロパティ項目の取得」エンドポイント(`GET /v1/pages/{page_id}/properties/{property_id}`)でページネーションして全件取得する。
- 対象になりやすいプロパティ: 顧客の対応履歴・案件・タグ・関連アカウント・次回アクションなどの被リレーション。件数が多い一覧はそもそもプロパティからではなくSupabaseインデックスから取得する設計とし、プロパティ全件取得は同期・整合性確認時に限定する。

## 12. 標準ビューの作成(Notion側の閲覧性)

`setup-notion.ts` は、ビュー作成API(`POST /v1/views`、APIバージョン `2026-03-11`)で以下の標準ビューを作成する。Notionを閲覧中心で使うメンバーがアプリなしでも主要な切り口で見られるようにする。

| ビュー | 対象DB | 種類・条件 |
|---|---|---|
| 全顧客 | 顧客アカウント | table。アーカイブ=false、表示順=最終対応日降順 |
| 営業ステータス別 | 顧客アカウント | board(営業ステータスでグループ) |
| 事業区分別 | 顧客アカウント | table(事業区分のquick_filter付き) |
| 本日・期限超過アクション | 次回アクション | table。状態=未完了、期限が今日以前、期限昇順 |
| 最新対応履歴 | 対応履歴 | table。対応日時降順 |
| 未解決クレーム | クレーム | table。対応状況≠完了、対応期限昇順 |
| 有効契約 | 契約 | table。状態=有効、契約終了日昇順 |

- 「自分の担当顧客」に相当する動的ビュー(閲覧者本人でフィルタ)はAPIのフィルタでは表現できないため、**自社担当者のquick_filterを付けた「担当者別」ビュー**を作成し、個人固定のビューは各自がNotion上で追加する運用とする。
- ビューはNotion上で利用者が編集し得るため、正とはみなさない(再セットアップ時に再作成可能)。

## 13. Notion運用ルール(利用者向けに周知する事項)

- 登録・更新は専用Webアプリを推奨。Notionは閲覧中心。
- Notion側で直接編集した場合もWebhook経由でアプリの検索インデックスへ同期される。ただし必須項目チェック等は効かないため、警告が管理画面に出ることがある。
- **Notion側でページを削除(ゴミ箱へ移動)しないこと**(特に対応履歴)。`in_trash` が検知された場合は即時反映せず、管理者の確認対象になる。
- **external_idプロパティ、導出キャッシュ項目(最新対応内容・次回アクション等)をNotion側で編集しないこと。** 編集しても再計算で上書きされる。
- マスタ(営業マスタDB)の編集はアプリの管理画面から行うこと。
