## 1. 背景と目的

営業情報がExcel、Googleスプレッドシート、Notionに分散しており、検索性・更新性・監査性に問題がある。これを専用Webアプリに集約し、以下を実現する。

- 顧客情報の一元管理と高速検索
- 営業活動履歴・案件・契約・クレームの記録と管理
- 次回アクション管理、営業担当者ごとの活動管理
- CSVによる既存データ移行(1,000〜10,000件規模)
- Notionからも情報を確認できる状態の維持
- 誰が・いつ・何を編集したかの監査
- 社内メンバー以外も利用できる権限管理

## 2. 最重要方針(優先順位)

1. 見やすさ
2. 検索のしやすさ
3. 情報登録のしやすさ
4. 情報更新のしやすさ
5. 営業担当者が迷わず操作できること
6. 情報量が多くても必要な情報へ素早くアクセスできること
7. 操作回数・画面遷移・不要なモーダルを減らすこと
8. 利用者・顧客データが増えても破綻しないこと

## 3. 事業区分

- インソールを軸にした介護福祉領域の事業
- AIセミナー事業

顧客は同一システムで管理し、事業区分・タグで分類する。同一顧客が両事業の営業対象になり得る。**事業区分はコードに固定値として埋め込まず、管理画面から追加・変更・無効化できる**(マスタ管理)。

## 4. データの正本(Single Source of Truth)

- **顧客・案件・対応履歴・契約・クレーム・営業マスタ等の営業データの正本はNotion**とする。
- Supabaseの役割は認証・権限・検索インデックス・監査ログ・同期状態・ジョブ管理に限定する。
- SupabaseへのキャッシュはNotion正本の派生データであり、境界は [architecture.md の SSoT境界](./architecture.md#3-ssot境界) に定義する。
- ブラウザからNotion APIを直接呼び出さない。Notionトークン・Supabase Secret key・Webhook Secretはサーバー側のみで保持する。

## 5. 機能要件

### 5.1 認証・ユーザー管理

- メールアドレス+パスワードログイン、Googleアカウントログイン
- パスワード再設定
- 一般公開の自由登録は不可。管理者から招待されたユーザーのみ利用可能
- 権限は4段階: **管理者 / A権限 / B権限 / 閲覧専用**(詳細は [permissions.md](./permissions.md))
- 権限制御はUI表示・サーバー処理・データベース(RLS)の3層で実施

### 5.2 顧客アカウント管理

- 顧客管理の基本単位は法人または事業所・部署単位の「顧客アカウント」
  - 例: 「株式会社A AI事業部」「株式会社A 介護事業部」「株式会社A 東京営業所」はそれぞれ独立した顧客アカウント
- 法人グループをまとめる独立レコードは作らない。各顧客アカウントに自己参照型の「関連アカウント」を持たせる
- 顧客詳細画面に関連アカウントを表示し、クリックで該当アカウントの詳細へ遷移できる
- 登録・編集・アーカイブ(ハード削除はしない)
- 顧客担当者(先方担当者)を顧客アカウントに紐付けて管理

### 5.3 案件管理

- 1つの顧客アカウントに複数案件を登録できる
- 案件名・事業区分・商材・営業ステージ・見込み金額・契約金額・確度・受注予定日・失注理由等を管理

### 5.4 対応履歴

- 時系列表示。通常時は「日時・分類・タイトル・登録者・次回予定日」のみコンパクト表示し、ワンクリックで展開
- 1件の履歴に**複数の分類**(電話・資料送付・見積発行など)を設定できる
- 複数顧客を選択して同一内容を**一括登録**できる。履歴レコードは顧客ごとに独立して作成し、共通の `batch_id` を持たせる(共有レコード禁止)。一括登録前に対象件数と内容の確認画面を表示
- **編集可・削除禁止**。編集時は変更前後の値(変更項目のみ)・実行者・日時・対象NotionページID・操作元・リクエストIDを監査ログへ保存
- 本文はNotionページ本文ブロックに保存し、DBプロパティには一覧用の要約のみを置く。本文変更の監査は本文ハッシュ・要約・文字数で行う([notion-schema.md §10](./notion-schema.md#10-長文の扱いページ本文ブロック))
- Notion上の作成者はAPIインテグレーション名になるため、アプリ上の実行者(登録者・最終編集者のアプリユーザーIDと氏名)を別プロパティとして必ず保存

### 5.5 契約・クレーム

- 契約・クレームは対応履歴に混在させず、顧客詳細の専用セクションで管理
- 契約: 契約区分・取引区分・金額・期間・自動更新・請求条件・支払状況・契約書URL/ファイル等
- クレーム: 発生日・重要度・対応責任者・対応期限・対応状況・原因・再発防止策等(詳細本文はNotionページ本文で管理)

### 5.5.1 次回アクション管理

- 次回アクションは専用のNotion DB(次回アクションDB)を**正本**として管理する([notion-schema.md §7](./notion-schema.md#7-次回アクション-db新規9つ目))
- 対応履歴の登録時に入力した次回アクションから正本レコードを自動作成する
- 顧客・案件に表示する「次回アクション・次回予定日」は、未完了アクションのうち期限最短のものからアプリが自動導出する(重複した正本を作らない)
- マイデスクの本日対応予定・期限超過は次回アクションのインデックス(action_index)を正式な参照元とする
- アクションは完了・取消の状態管理を行い、完了日時を記録する

### 5.6 検索

- 検索対象: 法人名・事業所名・施設名・部署名・電話番号・都道府県・住所・代表者名・顧客担当者名・メールアドレス・タグ・事業区分・営業ステータス・自社担当者・集客ルート
- 電話番号はハイフンなしで正規化して保存・検索(表示時は整形可)
- 表記揺れの吸収: 株式会社/(株)/㈱、有限会社/(有)/㈲、全角半角、スペース有無、英字大文字小文字、電話番号ハイフン、髙/高、﨑/崎、邊/辺、ひらがな/カタカナ、一部の住所表記揺れ
- 完全一致・部分一致・前方一致・類似検索の使い分け。人名・会社名の曖昧検索は誤結合を起こさない範囲で実装
- 複合絞り込み: 複数タグ(AND/OR切替)・複数事業区分・営業ステータス・自社担当者・都道府県・集客ルート・次回予定日期間・最終対応日期間・見込み金額・優先度
- 保存済み検索(例: 自分の本日対応予定、AIセミナー対象で未接触、神奈川県の介護施設、次回予定日超過)

### 5.7 CSVインポート・エクスポート

[csv-import-design.md](./csv-import-design.md) に準拠。要点:

- CSVファイルはSupabase Storageのprivate bucketへ署名付きURLで直接アップロードする(サーバー関数のボディで受けない)。原本は30日で削除
- インポートはアップロード→文字コード/ヘッダー確認→列マッピング→正規化→バリデーション→重複判定→プレビュー→利用者確認→本登録→完了表示の10ステップ
- 重複判定: ①電話番号完全一致 ②正規化法人名+事業所名 ③正規化法人名+都道府県 ④類似度の高いものは候補表示。**自動統合禁止**
- 重複候補ごとに「新規登録/既存更新/取り込まない」を一括・個別で選択可能
- Notion APIレート制限(平均3req/s、429+Retry-After遵守)を守るジョブ実行。分散レート制御・再試行・指数バックオフ・決定的external_idによる冪等化・中断後再開・エラーレポート
- エクスポートは2方式: 高速(検索インデックスの一覧項目のみ・即時)/ 完全(Notion正本の全プロパティ・ジョブ実行)。全件/検索結果/選択顧客、出力列選択、UTF-8 BOM付き、CSVインジェクション対策

### 5.8 マスタ管理

管理者が以下の**システム対応済みマスタ種別内の選択肢**を追加・編集・並び替え・無効化できる(コードへの固定埋め込み禁止)。

- 事業区分 / タグ / 営業ステータス / 案件ステージ / 対応履歴分類 / 集客ルート / 優先度 / 契約区分 / クレーム重要度 / アクション状態 / その他対応済み選択項目

補足:

- **新しいマスタ種別そのもの**の追加は、参照プロパティ・画面・インデックス列を伴うため、カスタム項目エンジンを実装しない限りコード・スキーマ対応が必要(管理画面からは行えない)
- 各マスタは `semantic_key`(won / lost / meeting / active / completed 等)を持ち、集計・判定は表示名ではなくsemantic_keyで行う(名称変更でロジックが壊れない)

初期データ(叩き台):

- 営業ステータス: 未接触 / 接触予定 / 接触中 / 担当者接続 / アポイント獲得 / 商談中 / 提案・見積 / 検討中 / 受注 / 導入・実施中 / 継続フォロー / 保留 / 失注
- 集客ルート: 紹介 / セミナー / 広告 / Web問い合わせ / 展示会 / アウトバウンド / 既存顧客 / パートナー / 自治体・団体経由 / その他

事業区分ごとに利用できるステータスを制御できる拡張性を持たせる(初期版では全事業区分共通で運用可)。

### 5.9 同期

[sync-design.md](./sync-design.md) に準拠。要点:

- アプリからの更新: 認証→権限→検証→Notion現在値取得→差分計算→Notion更新→監査ログ→検索インデックス更新→応答
- Notion更新成功後のSupabase側失敗は放置せず、同期エラーとして記録し管理画面から再実行可能
- Notion側の変更はWebhookで検知し、再取得してインデックス更新
- Notion側の削除は即時削除せず「削除確認待ち」とし、管理者が確認して除外/復旧を選択
- 定期整合性確認でWebhook取りこぼしを回収

### 5.10 監査ログ

- 追記専用。通常利用者は更新・削除不可
- 記録対象: 顧客/案件/対応履歴/契約/クレームの作成・更新、CSVインポート/エクスポート、一括更新、権限変更、ユーザー招待・無効化、マスタ変更、Notion同期、同期エラー、Notion側変更検知
- 変更された項目のみのbefore/afterを保存(全レコード複製はしない)。添付ファイル本体や巨大データは保存しない

### 5.11 削除方針

- 対応履歴は**削除禁止**
- その他の主要データもハード削除は避け、アーカイブ・無効化・取消・解約・完了・重複統合済みの状態遷移で扱う
- 物理削除が必要な場合は管理者のみとし、実装前に理由とリスクを文書で説明する

## 6. 画面要件

詳細は [ui-guidelines.md](./ui-guidelines.md)。初期版の必須画面:

1. ログイン(メール+パスワード / Google / パスワード再設定)
2. マイデスク(本日対応予定・期限超過・KPI・担当顧客/案件・最近閲覧/更新。集計値クリックで条件付き一覧へ遷移)
3. 顧客検索・一覧(高密度テーブル、列グループ=基礎情報/営業情報、列表示切替・固定列・複数選択・一括履歴登録・URL検索条件保存・保存済み検索・簡易プレビュー)
4. 顧客詳細(ヘッダー+基礎情報枠+営業枠+対応履歴枠+契約・クレーム専用セクション)
5. ユーザープロフィール(営業ツール上の利用者プロフィール)
6. 管理画面(ユーザー・権限・マスタ・CSV・監査ログ・同期状況/エラー・Notion削除確認・システム設定)

## 7. 非機能要件

- 顧客1,000〜10,000件、対応履歴は将来数万件以上を想定
- 一覧・検索はSupabase検索インデックスを利用し、Notion APIを一覧表示のたびに大量呼び出ししない
- 詳細表示時はNotionの正式データを取得。短時間キャッシュ使用可(キャッシュが正式データでないことを明示)
- API障害時は利用者へ状況を分かりやすく表示。処理中の二重クリック防止。一部失敗時の再試行
- 日時は日本時間(JST)で表示。データベース内はUTCで一貫管理
- PCの一般的な業務環境で快適に動作。アクセシビリティとキーボード操作を考慮

## 8. セキュリティ要件

- Notionトークン / Supabase Secret key / Webhook Secretをクライアントへ渡さない
- 環境変数をリポジトリへコミットしない。`.env.example` を用意する
- Supabase RLS有効化。API単位でも権限確認。認証済みでも権限外操作を拒否
- 入力値はZodで検証。外部入力を信用しない
- CSVインジェクション防止。Webhook署名検証。二重送信防止
- CSRF / XSS / SQLインジェクション等の基本対策
- ログへパスワード・トークン・Cookieを出力しない。個人情報をエラーログへ過剰に残さない
- 管理画面へのアクセス制御を厳格にする

## 9. 初期版で実装しないもの(フェーズ2以降)

- AIによる履歴要約・営業提案・入力補助
- Gmail連携 / Googleカレンダー連携 / Slack連携
- 名刺読み取り / スマートフォン向け電話発信連携 / 高度なメール送信機能

ただし後から追加しやすい責務分離(通知・外部連携の抽象化ポイント)を意識する。

## 12. 設計上の仮定(承認済みの初期値)

| # | 項目 | 仮定 |
|---|------|------|
| 1 | Notionワークスペース | 9つのデータベースはセットアップスクリプト(Notion API)で新規作成する。既存DB流用が必要になった場合はマッピング層で吸収 |
| 2 | デプロイ先 | Vercel + Supabase(クラウド)。ジョブワーカーの毎分起動は**Supabase Cron(pg_cron + pg_net)を初期採用**(Vercel Hobbyの毎分Cron不可のため)。Vercel Pro以上を利用する場合はVercel Cronへ差し替え可能(JobScheduler抽象化) |
| 3 | Supabaseキャッシュ境界 | 一覧表示・検索・絞り込み・集計に使う項目のみキャッシュ。対応履歴本文・クレーム詳細等の長文はNotionページ本文のみ(詳細は architecture.md) |
| 4 | 移行元データ | サンプル未提供のため、標準的な顧客リスト列構成を想定した柔軟な列マッピングで対応 |
| 5 | Googleログイン | Googleアカウントでも招待済みメールアドレスのユーザーのみログイン可能。自由登録不可(Before User Created Hookで作成自体を拒否) |
| 6 | タイムゾーン | DB・API内部はUTC、表示はJST(Asia/Tokyo)固定 |
| 7 | ブランドカラー | 会社カラー(オレンジ)には寄せず、落ち着いたスレート系の独立カラーを採用 |
| 8 | Notion APIバージョン | `2026-03-11`(最新)。`@notionhq/client` は対応リリース以上。削除判定は `in_trash` |
| 9 | Supabase APIキー | レガシー `anon` / `service_role` は使用せず、Publishable key(`sb_publishable_...`)/ Secret key(`sb_secret_...`)を使用(レガシーキーは2026年末廃止予定) |
| 10 | データ保持期間 | CSV原本=30日、write_operations=90日、監査ログ=初期版では自動削除なし(恒久保存) |
| 11 | 顧客.見込み金額 | 進行中・保留案件の見込み金額合計からの**導出値**として確定。確度を乗じた加重見込み金額は将来のダッシュボード集計項目(フェーズ2以降) |
